# 容器界面性能检查与修复（2026-09-19）

## 项目中已确认的问题

- 0.9.0 的 ClientGuiLayoutCache 在打开容器时捕获一次，随后补捕 20 个渲染帧。preferCapture 使用内容签名数量的大于等于比较，相同布局仍可标脏。
- 客户端 tick 末只要脏标记为真，就同步调用 SlotLayoutData.writeAll(BY_POS) 和 Files.writeString，遍历全部已缓存容器并生成完整 JSON。不是所有空闲 tick 都保存，但捕获和锚点突发期间会反复占用客户端线程。
- 相同锚点也会更新同类容器并标脏；GUI 槽位近邻去重此前逐项扫描，槽位越多成本越高。
- 捕获尚未结束就关闭的界面可能留在 PENDING 中。

## 本次修复（两版本同步）

- 相同捕获和相同锚点不再次标脏；补捕保留已学到的能力槽编号。
- 更新停止 1 秒后合并保存；连续变化时约 5 秒提交一次。慢写盘期间最多一个后台任务，不按 tick 堆积任务。
- 客户端只在需要提交时复制容器映射，槽位列表不可变。JSON 编码、临时文件写入及原子替换均在专用后台线程执行。
- 写盘失败保留待保存状态，5 秒后重试；写盘过程中产生的新修改会继续保存，避免旧快照覆盖后丢失更新。
- 使用 10 像素网格进行近邻去重，保留原有距离和顺序语义；及时清理已关闭界面的补捕记录。
- 校准锚点日志改为仅实际改变时输出 debug；纠正 README 的“零 tick 事件、服务端零开销”表述。

## 尚需区分的开销

首次读取已有 slot-layouts.json 仍在客户端线程进行；非常大的旧缓存可能造成首次使用停顿。槽位校准在服务端每 5 tick 采样一次，七个朝向的能力查询和菜单/能力槽配对也可能在大型容器中产生开销。本次没有改变校准规则或禁用功能。

未取得玩家的 spark 采样，也未运行格雷科技奥德赛整合包，因此不能认定某个垃圾槽模组是原因，不能据此量化实际 FPS 改善或声称消除全部卡顿。快速退出或崩溃可能丢失尚在合并窗口内的新缓存；这不涉及玩家物品或 SFML 程序存档。

## 回归测试

LayoutCachePerformanceTest 覆盖：空闲 10000 tick 零快照；200 次突发更新合并一次；持续更新的最长等待；慢写盘的新修改；失败重试与执行器拒绝；真实后台 JSON 文件替换；重复锚点/捕获；不可变快照；2000 个随机槽位与原去重规则逐项一致。
